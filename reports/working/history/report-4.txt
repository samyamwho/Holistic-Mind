Abstract
This report presents the design and evaluation of a NoSQL data platform
for IoThings Home Automation Solutions, a UK smart-home company. The
company already uses relational databases for business areas such as billing,
CRM, sales and logistics. These systems are suitable for structured business
information, but they are less flexible when handling continuous sensor data
produced by different types of smart-home devices.
The implemented solution uses a three-node MongoDB replica set running
in Docker. The cluster uses keyfile authentication for communication between
MongoDB nodes and Role-Based Access Control (RBAC) for application ac-
cess. Sensor data is received through MQTT using a Node.js service with
an embedded Aedes broker. Incoming messages are temporarily buffered and
written to MongoDB in small batches using bulkWrite. A synthetic dataset
containing 3,000 events from 30 devices provides a controlled test environment
without using real household data.
The backend also contains automation rules that react to selected sensor
readings. Low soil moisture creates an irrigation event, while high plant tem-
perature creates a cooling mist event. Replica-set availability was tested by
stopping the primary MongoDB node and observing the election of a new pri-
mary. An Express.js REST API provides access to device information, event
history and analytical results.
The report also discusses the database concepts that informed the design,
including CAP, PACELC, ACID, BASE, replication, indexing and polyglot
persistence. ThefinalsystemdemonstrateshowMongoDBcancomplementan
existing relational environment when the application needs flexible data struc-
tures, continuouseventingestionandautomaticrecoveryfromadatabase-node
failure.

1 Introduction
1.1 About IoThings Home Automation Solutions
IoThings Home Automation Solutions is a UK-based smart-home company that
installs connected sensors and devices in residential properties. Its systems cover
areas such as home security, indoor climate monitoring, smoke and carbon monoxide
detection, and garden irrigation.
Thesedevicescontinuouslyproduceoperationaldata. Asprinklermayreportwhether
a valve is open, how long it has been active and how much water it has used. A
temperature sensor may report temperature and humidity values. A smart lock may
record whether a door is locked, how access was granted and whether tampering was
detected.
ThisinformationistransmittedusingMQTT,alightweightmessagingprotocolcom-
monly used in Internet of Things (IoT) systems. IoThings requires a reliable way
to receive, store and analyse these events so that the data can support automation,
customer information and operational monitoring.
1.2 Problem with the Existing Database Setup
IoThingsalreadyusesrelationaldatabasesforbusinessfunctionssuchasERP,CRM,
billing, orders and logistics. Relational databases are well suited to these areas
because the information has a predictable structure and clear relationships.
The requirements of IoT telemetry are different. Different devices produce differ-
ent fields, and sensor readings may arrive continuously. This creates three main
challenges:
1. Different device dataformats: A sprinkler, temperature sensor and smart
lock do not produce the same information. Storing every device type inside
one fixed relational table can result in many empty fields or repeated schema
changes.
2. Frequent write operations: As the number of connected devices grows,
many readings may arrive close together. Writing each event individually
places additional load on the database and application.
3. Availability: A single database server creates a single point of failure. If the
server becomes unavailable, sensor events cannot be stored until the database
is restored.

2 NoSQL Concepts Used in This Project
2.1 CAP Theorem
The CAP Theorem explains an important trade-off in distributed databases. When
a network partition occurs, a distributed system cannot fully guarantee all three of
the following properties at the same time:
• Consistency (C): users receive the latest valid version of the data;
• Availability (A): requests continue to receive responses; and
• Partition Tolerance (P): the system continues operating when communi-
cation between nodes is interrupted.
Network interruptions are possible in any distributed system, so partition tolerance
cannot simply be ignored. During a partition, a database must decide whether
maintaining a consistent view of the data or continuing to serve every request is
more important.
MongoDB replica sets favour a majority-based approach. A node that cannot com-
municate with enough voting members cannot safely continue acting as primary.
This reduces the risk of separate parts of the cluster accepting conflicting writes.
2.2 PACELC
CAP mainly describes behaviour during a network partition. PACELC extends this
idea by also considering normal operation:
If Partition: choose Availability or Consistency; Else: choose Latency or Consistency
(1)
The second part is important because most database activity occurs when the net-
work is operating normally. MongoDB provides settings such as writeConcern and
readPreference that influence this balance.
Forexample, awritecanrequireconfirmationfromamajorityofreplica-setmembers
before it is treated as successful. This provides stronger confirmation that the data
has reached multiple nodes, but it may take slightly longer than acknowledging the
write immediately on one node.
The appropriate configuration therefore depends on the importance of the data and
the acceptable response time.

2.3 ACID and BASE
Relational databases are commonly associated with ACID properties:
• Atomicity: a transaction completes fully or is rolled back;
• Consistency: database rules remain valid after a transaction;
• Isolation: concurrent transactions do not incorrectly interfere with each
other; and
• Durability: committed information remains stored after a system failure.
Distributed NoSQL discussions also commonly refer to BASE:
• BasicallyAvailable: theoverallserviceisdesignedtoremainavailablewhen
part of the system fails;
• Soft State: replica state may temporarily change while updates are being
distributed; and
• Eventual Consistency: replicas converge once the updates have been prop-
agated.
ACID and BASE should not be treated as two simple opposites. Modern databases
support different levels of transactional behaviour and consistency. The practical
requirement is to select behaviour that matches the application.
For IoThings, the important requirements are reliable storage of sensor events, tol-
erance of a database-node failure and sufficient flexibility to support several types
of devices.
2.4 Main Types of NoSQL Databases
2.4.1 Document Databases
Document databases such as MongoDB store information in JSON-like documents.
A document can contain nested fields, arrays and different values depending on the
type of record.
This fits the IoThings scenario because different devices do not produce identical
telemetry. A common document structure can store fields such as device ID and
timestamp, while a nested payload stores information specific to the sensor.
The main design consideration is that documents still need a clear structure. Flex-
ible schema design does not mean that fields should be added without planning.
MongoDB also has a 16MB maximum document size, which means continuously
growing data should not be stored inside one unlimited document.

2.4.2 Key-Value Databases
Key-value databases such as Redis organise information as a key and its associated
value. They are effective for direct lookups and are commonly used for caching,
session data and frequently accessed application state.
Their simple structure provides fast access, but they are less suitable when the
application requires detailed filtering across many attributes.
2.4.3 Wide-Column Databases
Wide-column databases such as Apache Cassandra are designed for large distributed
datasets and high write volumes. They are particularly effective when the expected
query patterns are known before the database schema is designed.
Thetrade-offisthatad-hocqueryingismorerestrictedthaninadocumentdatabase.
2.4.4 Graph Databases
Graph databases such as Neo4j place relationships at the centre of the data model.
They are useful for problems where connections between entities are important, such
as social networks, recommendation relationships and fraud analysis.
The main requirement in this project is the storage and retrieval of sensor events
rather than complex relationship traversal. A document database therefore provides
a more direct fit.

3 Relational Databases vs. MongoDB
3.1 How the Data Models Differ
Relational databases store information in tables with defined columns and relation-
ships. This model is effective for structured business information such as invoices,
payments, customers, orders and financial records.
MongoDB stores information as documents. Related values can remain together in
one document, and documents within the same collection can contain different fields
where necessary.
This difference is important for IoThings. A sprinkler produces water-related values,
while a smart lock produces access and security information. Requiring both devices
to follow exactly the same relational table structure would introduce unnecessary
complexity.
3.2 Flexible Schema
There are several possible ways to store varied sensor information in a relational
database.
One option is a large table containing every possible sensor field. This often results
in many NULL values because most fields are not relevant to every device.
Another approach is to create a separate table for each sensor type. This keeps
individual tables clear but makes combined queries across all device activity more
complicated.
A third option is an Entity-Attribute-Value structure, where values are stored as
generic attribute records. This provides flexibility but makes even simple queries
harder to understand.
MongoDB provides a simpler model for the requirements of this project. Every sen-
sor event contains common fields such as device_id, household_id, sensor_type
and timestamp. Device-specific values are stored inside the nested payload object.
As a result, the collection retains a consistent overall structure while still supporting
different sensor types.

3.3 Scaling
Traditional relational systems commonly increase capacity through vertical scaling.
This means moving the database to a machine with more CPU, memory or storage.
MongoDB also supports horizontal scaling. At a larger scale, MongoDB collections
can be distributed across several servers through sharding.
Sharding is not required for the current project because the test dataset is relatively
small. However, the MongoDB data model provides a clear route for expansion if
IoThings later operates a much larger number of devices and households.
3.4 Using SQL and NoSQL Together
The use of MongoDB does not require IoThings to replace its existing relational
databases.
A more practical design is to assign each database technology to the data it handles
best:
• Relational database: billing, finance, orders, inventory and other struc-
tured business records;
• MongoDB: sensor events, device activity, telemetry and IoT analytics.
This approach is commonly described as polyglot persistence. Instead of selecting
one database technology for every part of the company, different database systems
support different workloads.
For IoThings, this preserves the reliability of its existing transactional systems while
introducing a document database specifically for the less predictable structure and
higher write frequency of IoT data.

4.2 Architecture Design Rationale
The architecture was selected according to the characteristics of smart-home teleme-
try.
Sensordatadiffersfromconventionalbusinessrecordsbecauseitarrivescontinuously
and the structure depends on the device producing it. A temperature sensor may
report temperature and humidity, while a sprinkler records valve state, water flow
and total consumption. MongoDB’s document model provides enough flexibility
for these differences while maintaining a common structure for identification and
timestamps.
Node.js forms the application layer between MQTT, MongoDB and the API. Keep-
ing the main processing logic in one service makes the flow of information easier to
follow. Incoming MQTT events are validated and buffered, automation rules are
evaluated, database writes are performed and API requests are handled through the
same application layer.
The three-node MongoDB replica set addresses a different requirement: availabil-
ity. With a single database node, a database failure would prevent the backend
from storing new events. The replica set keeps multiple synchronized copies of the
database and allows another member to become primary when the current primary
becomes unavailable.
The design therefore separates responsibilities clearly. MQTT handles message de-
livery, Node.js handles application processing, MongoDB stores the events, and the
REST API provides controlled access to the stored information.
4.3 Three-Node Replica Set
A three-node MongoDB replica set named rs0 was implemented using Docker.
The configuration contains:
• mongo1: normally the primary node, with election priority 2;
• mongo2: a secondary node with election priority 1; and
• mongo3: a second secondary node with election priority 1.
During normal operation, the primary accepts write operations. The secondary
members maintain replicated copies of the database and participate in replica-set
elections.

4.4 Replication and Failover
MongoDB replica-set members send heartbeat messages to monitor the state of the
other members. If the primary becomes unavailable, the remaining voting members
can hold an election.
With three voting members, two votes form a majority:

Writes accepted by the primary are recorded in MongoDB’s operations log, com-
monly called the oplog. Secondary nodes read these operations and apply them
locally so that their copies remain synchronized.
This mechanism supports recovery from the loss of one replica-set member while
retaining enough nodes to form a majority.

4.5 Docker Networking and Port Mapping
The Docker configuration also separates the internal MongoDB ports from the ports
exposed on the host computer.
Inside Docker, each MongoDB container has its own network namespace. This
allows all three MongoDB services to use the normal internal MongoDB port, 27017,
without creating a conflict.
Within the Docker network, the nodes communicate using:
• mongo1:27017
• mongo2:27017
• mongo3:27017
For access from the host machine, the containers are mapped to separate ports:
• mongo1:27017 →localhost:27017
• mongo2:27017 →localhost:27018
• mongo3:27017 →localhost:27019
This distinction is important because the replica-set members communicate using
their Docker hostnames rather than the external host-port mappings. The host
mappings remain useful for administration and inspection through tools such as
MongoDB Compass or the Mongo shell.
4.6 Security
Two main security controls are included in the MongoDB configuration.
• Keyfile authentication: the MongoDB nodes share a protected keyfile. A
MongoDB instance that does not possess the correct key cannot authenticate
as a trusted replica-set member.
• Role-Based Access Control: the administrative account and application
account have separate responsibilities. Cluster administration is performed
through the administrator account, while the Node.js application connects
using its own restricted database account.
Separating these accounts follows the principle of least privilege. The application
does not require full cluster-administration permissions for normal sensor ingestion
and API operations.

4.10 Evaluation of the Failover Test
The test demonstrates more than the presence of three database containers. It
confirms that the replica-set election mechanism operates when the current primary
disappears.
Before the failure, mongo1 controlled normal read/write activity. Once it was
stopped, the two remaining members still formed a majority. They were therefore
able to elect mongo2 as the new primary without changing the replica-set configura-
tion manually.
An important observation is that restarting mongo1 did not automatically restore

5.2 Micro-Batch Ingestion
Writing every sensor event to MongoDB as a separate request would work at a small
scale, but it creates additional database and network overhead when many devices
are active.
The implemented service therefore uses a small in-memory message buffer.
A batch is written when either:
• the buffer reaches 50 events; or
20
--- PAGE 22 ---
Birmingham City University CMP6207 – Modern Data Stores
• 1,000 milliseconds pass before the buffer becomes full.
MongoDB’s bulkWrite operation then writes the collected events together.
Thisapproachprovidesabalancebetweendatabaseefficiencyandeventdelay. Wait-
ing only for 50 events would be unsuitable during periods of low activity because
a partially filled buffer could remain in memory for too long. The time-based flush
ensures that low-volume traffic is still written regularly.
At the same time, the batch size prevents every incoming MQTT message from
creating a separate database request during higher activity.
The selected values are appropriate for the scale of the current implementation.
Larger deployments would require performance testing to determine suitable val-
ues based on event rate, acceptable latency, available memory and database write
capacity.
5.3 Automation Rules
The backend evaluates selected sensor values when new telemetry arrives.
Three automation conditions are included in the implementation:
1. High plant temperature: when plant temperature rises above 28.0◦C, the
backend creates a cooling sprinkler event for the same zone.
2. Low soil moisture: when soil moisture falls below 25%, the backend creates
a 15-minute irrigation event.
3. Smoke or carbon monoxide alert: when smoke is detected or carbon
monoxide exceeds the configured threshold, the backend records the safety
event and processes the associated alert behaviour.
The automation logic shows how sensor data moves beyond passive storage. An
incoming value can immediately influence another system action while both the
original reading and the resulting event remain recorded in MongoDB.

6.4 Testing Scope and Limitations
The implementation confirms the main functional requirements of the proposed
design, but the test environment has clear limits.
The dataset contains 3,000 synthetic events produced across 30 devices. This is
sufficient to confirm document storage, indexing, API behaviour, automation logic
and replica-set operation. It does not represent the volume that would be generated
by thousands of homes over several months or years.
The use of synthetic data was deliberate. Smart-home telemetry may reveal infor-
mation about behaviour inside a household, including when devices are used and
when people may be present. Testing with generated identifiers and generated read-
ings removes the need to expose real customer data while retaining realistic database
structures.
The MongoDB nodes also run as Docker containers in the project environment.
Each container behaves as a separate service, which is useful for testing replication
and elections. However, containers running on one physical host do not provide the
same level of fault isolation as replica-set members running on separate physical or
cloud machines.
For example, stopping one MongoDB container tests a database-node failure. It
does not simulate the complete failure of the host computer, because all containers
depend on the same underlying machine.
A production evaluation would therefore require additional testing across separate
hosts. ItwouldalsoneedsustainedMQTTtraffic, simultaneousAPIrequests, longer
test periods and deliberate network interruptions between database members.

7 Conclusion and Future Work
7.1 Evaluation of the Proposed System
The completed implementation shows that MongoDB is suitable for the IoThings
telemetry workload represented in this project.
The document model supports several sensor types without requiring a separate
rigid structure for every device. Common identification fields remain consistent,
while device-specific measurements are stored inside nested payload data.
The three-node replica set improves database availability compared with a single-
node design. The failover test confirmed that the remaining members could elect a
new primary when the original primary became unavailable.
The MQTT and Node.js pipeline provides a clear path from incoming sensor mes-
sages to database storage and automation logic. Micro-batching reduces the number
of separate database writes without introducing a long delay for low-volume sensor
traffic.
The API and aggregation pipelines also show that the stored telemetry is useful
beyond simple event storage. The application can retrieve device history, calculate
water usage and identify events that match operational conditions.
7.2 Business Value
The stored telemetry provides useful information for both operations and customer-
facing services.
• Water-use reporting: sprinkler events record cycle duration, flow rate and
water consumption, allowing usage to be summarised over time.
• Battery monitoring: telemetry fields can identify devices whose battery
levels are decreasing and require maintenance.
• Safety monitoring: smoke, carbon monoxide and security events can be
stored with timestamps for later review.
• Device history: indexed event records provide a clear record of how indi-
vidual smart-home devices have behaved.
These functions demonstrate that the database has value both as an operational
data store and as a source of information for future reporting.

7.3 Future Work
The next stage of development should focus on scale, monitoring and deployment
outside a single development host.
A web or mobile dashboard would provide a visual interface for device activity,
irrigation usage and safety events.
Weather information could also be incorporated into irrigation logic so that recent
rainfall and forecast conditions are considered together with soil-moisture readings.
The database should be tested with a larger dataset and a higher rate of concurrent
MQTT events. This would provide clearer evidence about how the batching strategy
and indexes behave under sustained load.
Monitoring should also be expanded so that database health, MQTT connectivity
and failed automation actions are visible without relying only on terminal output.
Ifthenumberofconnectedhouseholdseventuallyexceedsthecapacityofareplicaset
on one database cluster, MongoDB sharding could be investigated. Sharding would
only be appropriate after actual workload measurements showed that horizontal
partitioning was required.
Overall, the project demonstrates a practical MongoDB-based architecture for Io-
Things. It supports varied IoT data, MQTT ingestion, automated actions, indexed
analytics and replica-set failover while allowing the existing relational databases to
remain responsible for structured business information.
